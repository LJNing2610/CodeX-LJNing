# 通用工程经验

本文件从工作台踩坑记录中提炼可复用结论，已去除用户名、路径、网络、账户、硬件与个人偏好。

## 定位问题

- 先找到共享调用链，再在根因位置修复；只修一个症状路径会留下同类故障。
- 用时间线、进程、配置、实际运行状态相互验证，不能只凭名称或单次查询判断。
- 平台工具输出可能本地化，优先使用结构化 API，不要硬编码英文标签解析。
- 服务、计划任务和后台程序要分别核对启动状态与最近执行结果。

## Windows 脚本

- PowerShell 脚本交付给 Windows PowerShell 5.1 时，注意 UTF-8 BOM 与编码识别差异。
- 写 Python 等源文件时使用无 BOM UTF-8，避免解释器把 BOM 当成语法错误。
- 内嵌 C# 时优先使用字符串数组拼接，降低 here-string 换行解析风险。
- 提权操作写成独立 `.ps1` 文件并用 `-File` 启动，避免复杂引号被重新解析。
- 修改注册表、服务或启动项前导出原值，并提供可执行的还原脚本。

## 可靠性

- 禁用错误报告或诊断服务前，必须同时建立崩溃日志或转储采集方案。
- 不直接删除受系统保护的驱动文件，使用 `pnputil` 等官方接口卸载。
- 网络服务与工具端口从环境变量或配置读取，避免多组件硬编码。
- 第三方 API 调用应有超时、错误处理和明确的降级路径。
- 安装、升级或修复失败时，先区分“配置错误、文件缺失、身份认证、平台限制”，不要直接重装。

## 仓库与密钥

- 推送前检查密钥、账户标识、会话、日志和大型二进制。
- `.gitignore` 只能阻止未跟踪文件；已经提交的敏感内容必须单独清理历史。
- 首次推送私有仓库前验证 Git 凭据；不要让用户把 Token 粘贴到对话或文档。
- 恢复包应包含配置骨架和安装步骤，凭据在本机重新授权。
