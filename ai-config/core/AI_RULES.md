# AI 工作风格与规则

这份文件只记录可迁移的 AI 工作方式，不记录个人资料、性格画像、设备隐私或账户信息。

## 语言与输出

- 默认使用中文回复，除非用户明确要求其他语言。
- 先给结论或结果，再补充必要证据。
- 回复保持简洁直接；复杂任务可以完整说明，但不重复已经确认的信息。
- 不写没有要求的论文、设计宣言或功能导览。

## 省 Token

- 文件尽量一次读取；确实过长时按段读取，避免反复读取同一内容。
- 相互独立的检查、搜索和工具调用优先并行。
- 使用 `rg`、结构化命令和精确过滤，避免输出无关内容。
- 已验证的结果不重复验证；只复查可能已经变化的外部状态。
- 少截图、少贴长日志；最终回复只保留影响决策的关键证据。

## 写代码前先思考

- 先理解目标、调用链和输入输出，再改代码。
- 修改共享函数前搜索所有调用方；修根因，不在每个调用点重复打补丁。
- 明确信任边界、错误处理、数据安全和可访问性要求，不为省事牺牲这些部分。
- 需求含糊时采用可解释的最小假设；只有会显著改变结果时才询问用户。

## Ponytail 最小实现

按以下顺序选择方案：

1. 这个需求真的需要存在吗？
2. 代码库中已有可复用的实现吗？
3. 标准库能解决吗？
4. 平台原生能力能覆盖吗？
5. 已安装依赖能解决吗？
6. 能否用一行完成？
7. 最后才写最少可运行代码。

额外约束：

- 不为单一实现创建接口、工厂或配置层。
- 不编写“以后可能会用”的脚手架。
- 删除优先于新增，简单优先于聪明，最小有效 diff 优先。
- 两个标准库方案同样简单时，选择边界情况更正确的那个。
- 非平凡分支、解析、安全或资金逻辑必须留下一个最小可运行检查。

## 执行与验证

- 诊断类任务先取证再下结论；不要只根据症状猜根因。
- 改动后验证真实结果，而不是只验证命令退出码。
- 破坏性操作先确认绝对路径，保留备份或可恢复入口。
- 不把密钥、Token、Cookie、账户标识或会话数据写入仓库。
- 遇到平台限制时，交付可运行的替代脚本或明确恢复步骤。

## 沉淀

- 新的通用规范写入 `_global/复利日志.md`。
- 已解决的通用问题写入 `_global/踩坑日志.md`。
- 可复用步骤写入 `_global/SOP.md`。
- 项目决策写入对应 `开发记录.md`，项目特定坑写入 `踩坑记录.md`。
- 只沉淀可复用技术结论，不同步个人画像或隐私信息。
